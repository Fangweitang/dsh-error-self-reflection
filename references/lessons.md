# 故障模式与规则（lessons）

> 每条都由一次真实事故沉淀而来，已脱敏。
> 格式：**症状** / **容易犯的误判** / **实际机制** / **规则**（可执行）。
> 追加新条目请保持这个格式；`scripts/reflect.mjs promote` 可以生成草稿。

---

## 1. 为了"顺手对齐"改掉全局默认模型配置

- **症状**：安装某个插件后，整个会话开始无法正常工作。
- **容易犯的误判**：在 profile 里看到 `provider: X`，但在代码库里搜不到 `X` 的注册语句，
  于是判定它是失效配置，改成了自己认为"更正确"的 provider。
- **实际机制**：`provider` 可能由内置 bundle（`app.asar`）或远程配置提供，**搜不到注册代码不等于不存在**。
  而且 `agent-default-model` 是**全局默认模型**，改动影响所有会话；待装插件通常只应影响它接管的请求。
- **规则**：
  - 安装类任务**一次只改一个变量**，不要连带改与安装目标无关的全局配置。
  - 判断某个 provider/id 是否有效，以**实际运行日志**为准，不以 grep 结果为准。
  - 改全局配置前先声明范围（`diff --scope`），越界即报警。

## 2. 验证停在中间环节，就宣称"已验证兼容"

- **症状**：声称"已实测通过"，随后功能仍然失败。
- **容易犯的误判**：插件健康检查返回正常、配置文件能被解析、依赖都能 import，
  就认为整条链路可用。
- **实际机制**：这些只覆盖**中间环节**。真正决定行为的是组合后的运行时取值，例如：
  - 插件实际读到的 mode（可能配置写了 `auto` 而运行时是 `manual`）
  - 改动后的 provider/model 是否真的被请求采用
  - loader 组合后的最终 entry 集合
- **规则**：**验证必须覆盖最终产物**。重启后检查运行时返回值（HTTP 路由、日志、实际请求），
  而不是只读文件、只看健康检查。

---

## 3. 把"文档里引用危险字符"误判为"粘贴残留"（工具误报）

- **症状**：校验程序在说明文档里报出 HTML 片段残留，但文档本身是干净的。
- **实际机制**：文档为了举例**引用**了这些字符；正则只看字面，不看上下文。
- **规则**：**误报会让使用者放弃工具**。凡是对文本做模式匹配，
  必须排除注释行、反引号包裹的内联代码、说明性上下文的表格单元格。
  宁可少报一条，也不要制造噪音。

---

## 4. 把框架内置包当成"缺失依赖"

- **症状**：校验报出多个 `@scope/base` 之类的包不在 `node_modules`，看起来像安装损坏。
- **实际机制**：这类包由框架本体（如 `app.asar`）提供，本来就不在用户 profile 的 `node_modules` 里。
- **规则**：区分「内置提供」与「需落地安装」。内置包缺失是**正常**；第三方包缺失才是错误。
  同样的道理适用于 peer 依赖：内置 peer 与 shell 冻结表提供的模块应跳过。

---

## 5. 大文件"下载完成"其实是被截断的

- **症状**：分片并发下载跑完，退出码 0，但文件哈希对不上，或个别分片只有几百 KB。
- **容易犯的误判**：把 curl/下载器的退出码 0 当作成功。
- **实际机制**：源端中途断流时，下载器仍可能正常退出并留下**部分文件**。
- **规则**：大文件必须
  1. **逐片校验长度**（每片实际字节 == 区间长度）
  2. 全文件再算 SHA-256 与清单比对
  只信哈希，不信退出码和"文件存在"。

---

## 6. 包管理器卡住时，先分辨是"解析"还是"下载"

- **症状**：`pip install -r lock.txt` 长时间无进展。
- **容易犯的误判**：以为只是网络慢，继续等。
- **实际机制**：可能是**依赖回溯求解**卡住，根本没开始下载。
- **规则**：看缓存里有没有增长的大文件——
  没有实际字节增长而进程仍活着，基本是解析阶段。
  解析卡住时改用手取 wheel + `--no-index --no-deps` 本地安装，或改用镜像索引安装其余依赖。

## 7. 写机器可解析文件时带上 BOM

- **症状**：JSON/YAML 解析器报 `expected value at line 1 column 1`（或类似"首字符非法"）。
- **实际机制**：某些工具（尤其 Windows 上的 shell 命令）默认写 UTF-8 BOM，
  严格解析器把 BOM 当作非法首字符。
- **规则**：写机器可解析文件一律使用**无 BOM UTF-8**。
  Windows PowerShell 示例：
  `[IO.File]::WriteAllText($path, $text, (New-Object Text.UTF8Encoding($false)))`

## 8. 脚本里混入粘贴残留

- **症状**：运行时出现"无法将 '<' 项识别为 cmdlet/命令"之类与脚本内容无关的报错。
- **实际机制**：编辑脚本时混入了 HTML 片段或对话残留。
- **规则**：写完脚本先做**语法自检**（如 `node --check`），再运行。
  校验工具也应把这类残留当作可检测项。

---

## 9. 假设配置文件只由自己修改

- **症状**：写完配置，再次编辑时报"文件已被修改"；或改动"没有生效"。
- **实际机制**：用户或应用本身可能在同时写同一个配置文件。
- **规则**：不要绕过"文件已变更"的保护。**重新读取 → 基于最新内容重做修改**。
  写完后再次读取确认，不要假设"我写的就是最终态"。

---

## 10. 把"同一 id 出现多次"当成硬错误（过度结论）

- **症状**：看到同一个 entry id 在补丁文件里出现多次，直接认定这是配置损坏的原因。
- **实际机制**：Cordis 系的补丁语义中，带 `id` 且无 `insert` 的行是**覆盖**已有同 id 行。
  同一 id 多行**是合法的**（例如先配置、再 `disabled: true`）。
- **规则**：报告根因前先确认机制，**合法结构不要当作故障点**。
  真正会静默失效的是 **override 的 id 对不上任何插入行**（配置成为死代码）。
  另外，内置 bundle 的补丁文件在 `app.asar` 内，离线**无法确证**孤儿行——
  此时应表述为"无法离线确证"，而不是"一定是死代码"。

## 11. 静态搜不到就判定"运行时不存在"

- **症状**：在打包产物里 grep 不到某个全局对象/接口的定义文件，
  于是认定该契约不存在。
- **实际机制**：这类对象可能是**运行时注入的全局对象**（由 shell/引导脚本写入 `<head>`），
  其定义以字面量形式存在于某个模块里，而非独立文件。
- **规则**：判断运行时契约是否存在，查**文档化契约**与**注入点代码**，
  不要只搜唯一文件名。

---

## 12. 把终端显示乱码当成文件损坏

- **症状**：终端输出中文全是乱码，怀疑文件被写坏。
- **实际机制**：旧版 Windows 控制台的代码页问题；文件本身可能是正确 UTF-8。
- **规则**：怀疑编码损坏时，用脚本/语言运行时读**字节**判断
  （前 3 字节是否 `EF BB BF`、`U+FFFD` 出现次数），
  不要相信终端显示。判断后再决定是否重写文件。

---

## 13. 状态快照没有格式版本，导致 diff 产生大量假"新增"

- **症状**：修好解析逻辑后，用修复前拍的快照做对比，报出一大堆"新增"。
- **实际机制**：修复前解析失败，快照里对应字段为空；修复后有了数据，
  两侧一对比就全是"新增"。**快照结构变化会让旧快照失真。**
- **规则**：
  - 快照必须带 `schema` 版本字段；结构变化时 +1。
  - `diff` 遇到版本不符应**拒绝执行并提示重拍**，不要输出误导性结果。
  - 在 ESM 中加载外部模块用 `createRequire`，不要用 `eval('require')`（会静默失败）。

---

## 14. 用正则做"精确行替换"回滚，被换行符差异坑掉

- **症状**：正则替换"执行成功"但文件内容没变。
- **实际机制**：文件用 LF（`\n`）而模式里写了 CRLF（`\r\n`），一条都没匹配上。
- **规则**：
  - **回滚不要手写正则**，优先直接用备份文件覆盖。
  - 若必须按行改，先 `split("\n")` 观察真实换行符，不要假设跨平台一致。
  - 改完必须用 diff / 逐项对比**证明**回到了基线，不能只看"替换命令没报错"。

---

## 15. 把"自动发现问题"与"自动判断根因"混为一谈

- **症状**：设计自动化方案时，容易承诺"全自动防止再犯"。
- **实际机制**：工具能可靠拿到**证据**（某字段从 A 变成 B、某类问题第 N 次出现），
  但**根因**（为什么要改、这改动为什么有害）需要人判断。
- **规则**：
  - 自动部分：状态快照、字段级 diff、越界检测、指纹归类、复发计数、草稿生成。
  - 人工部分：确认问题真伪、补写根因、补写可执行规则。
  - 生成的草稿中，根因字段应显式标注"待补——工具无法推断"，不要用模板话术假装已想清楚。
